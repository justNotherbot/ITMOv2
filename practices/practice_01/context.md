## Context Pack для первого рабочего сценария

### Факты и правила

- Python 3.9; проект синхронный, без async
- Нельзя добавлять внешние зависимости
- Разрешено изменять только `context.md` и `problem.md`
- Источник изменений — `TRAINING_PR.diff`; цель — найти критические дефекты
- Формат фиксации дефектов: flow «candidate → evidence → check», «no evidence → skip»
- Definition of Done: для каждого дефекта есть evidence и воспроизводимая check

### Формат входа и результата

- Вход: HTTP POST `/api/reviews`, тело JSON: `{ "diff": string }`
- Выход: JSON: `{ "comment": string }`

### Ограничения и запрещённые действия

- Не добавлять новые библиотеки
- Не переделывать поток на async
- Не изменять файлы кода; в этой задаче фиксируем вывод в `context.md` и `problem.md`

### Хороший пример

Запрос:

```http
POST /api/reviews
Content-Type: application/json

{
  "diff": "diff --git a/file b/file\n..."
}
```

Ожидаемый ответ (пример):

```json
{ "comment": "Найдены проблемы ..." }
```

### Плохой пример

- Запрос без поля `diff` → в текущей реализации приведёт к 500 (KeyError)
- Слишком большой `diff` без ограничений → риск DoS и деградации времени ответа
- `diff`, содержащий инструкции для LLM (prompt injection), может привести к небезопасному ответу

### Что пока неизвестно

- Наличие внешних механизмов аутентификации/ограничения доступа на уровне шлюза/ingress
- Реализация `app.dependencies.review_service`
- Политика лимитов по размеру запроса и таймаутам

## Как использовали AI

- Для чего: базовое ревью diff и фиксация критических дефектов
- Тип промпта: zero-shot (Baseline), затем master prompt (при необходимости)
- Строка в `prompts.md`: см. запись `P1-01`
- Что проверили и исправили сами: сопоставили вывод с `TRAINING_PR.diff`, указали точные ссылки на строки и разработали воспроизводимые проверки
