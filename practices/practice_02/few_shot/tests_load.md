# Нагрузочные проверки

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| P95 при 256 КБ diff | llm: 5 tokens/sec (мок LLM, фиксированная генерация 300 мс, без внешнего сетевого джиттера) gateway: 5 RPS на POST `/api/reviews` с diff≈256 КБ (≈64k символов utf-8) duration: 10 мин steady-state + 1 мин warmup (не учитывается) | P95 response_latency < 1000 мс в 10-минутном окне — так как задержка при мок-LLM с фиксированным временем подчиняется нормальному распределению около 600±150 мс (gateway + LLM), хвост >1 с указывает на очередь или регресс | Задержка ответа (response_latency / http_request_duration_ms, миллисекунды, гистограмма gateway) ; Доля ошибок (http_error_rate, %, разбивка 4xx/5xx) ; Фактическая пропускная способность (throughput_rps, RPS) | k6/vegeta summary JSON + Grafana APM dashboard (панель p50/p95/p99 по http_request_duration_ms), трейсы gateway |
| Лимит размера | llm: 0 tokens/sec (вызов LLM не достигается, отсечка на валидации gateway) gateway: 1 RPS, payload diff 30k–35k символов (≈300–350 КБ utf-8, > лимита 256 КБ), последовательные запросы с интервалом 1 с duration: 2 мин (120 проб, достаточно для 100% статистики) | 100% ответов 413 Payload Too Large, p95 rejection_latency ≤ 500 мс — так как проверка размера синхронная на gateway и подчиняется детерминированному (почти константному) распределению <100 мс; любой 2xx или 5xx считается провалом | Код ответа HTTP (http_response_code, код, ожидаем 413) — доля 413 (%); Задержка отклонения (rejection_latency_ms, миллисекунды, p95); Счётчик вызовов LLM (llm_invocation_count, шт., должен быть 0) | Access-лог gateway (http_response_code histogram), k6 checks (status 413), метрика llm_invocation_count из логов сервиса |
| Стабильность таймаута LLM | llm: инъекция задержки 12 с (fault-injection мок LLM, эмуляция hanging generate) gateway: 1 RPS, POST `/api/reviews` diff≈1 КБ (минимальный валидный) duration: 5 мин (300 проб, каждая с ожиданием таймаута) | 100% ответов 503/504 за ≤11000 мс, 0% 500 — так как таймаут gateway детерминирован 10 с + 1 с grace и подчиняется равномерному распределению с жёсткой отсечкой на 10 с; ответ >11 с или 500 указывает на отсутствие маппинга исключения LLM | Доля 5xx по типам (http_5xx_by_code_ratio, %, разбивка 500 vs 503/504, требуем 0% 500); Задержка ответа при таймауте (timeout_response_latency_ms, миллисекунды, p100 ≤11000); Срабатывание защиты (circuit_breaker_trigger_count, шт.) | Логи gateway + OpenTelemetry трейсы gateway→llm-mock (span duration 12 с vs http status), гистограмма http_response_code, алерт на 500 |

Если нагрузочное тестирование пока не требуется, обоснуйте это и назовите условие, после которого оно понадобится.

## Как использовали AI

- Строка в [`prompts.md`](../prompts.md): P2-FS-01 (few-shot, см. `few_shot/experiment.md` — запрос с примерами хорошего/плохого).
- Что проверили и исправили сами: синхронизировали пороги с problem.md (P95 <1 с, лимит 256 КБ, таймаут 10 с); разделили нагрузку на llm/gateway/duration; добавили имена метрик с единицами (миллисекунды/проценты/RPS) и обоснование порогов через распределение; исключили добавление зависимостей и переход на async; отклонили общие формулировки «Время ответа, ошибки» без спецификации.
